# 提示词编写参考

先确定这次的目标、材料、范围和交付物，再从下列话术中选取能改善结果的部分。可以直接引用，也可以把意思写进提示词。优先遵循用户已明确的要求。局部问题按局部处理，需求已经清楚时直接推进。

## 1. 从第一性原理定位根因
<!-- 检索：第一性原理｜根因｜排查故障｜修复故障｜修复崩溃｜修复报错｜故障诊断 -->

> 从基本事实和约束出发，复现问题并沿因果链追查。用观察、日志或最小验证判断真正的原因，修复根因，并沿原来的操作路径验证结果。

## 2. 对齐偏好，再给三版方案
<!-- 检索：三版｜3版｜三套方案｜3套方案｜设计备选｜偏好不明确 -->

> 先问清会影响方案的几个关键问题，确认我对目标、风格和取舍的偏好。对齐之后给出三版有实质差异的方案，分别说明各自适用的场景和主要取舍。

## 3. 重新审视问题定义
<!-- 检索：问题定义｜底层需求｜需求诊断｜重新定义问题｜症状误认为原因｜手段误认为目标 -->

> 先判断我真正要达成的目标。检查当前问题的说法有没有把症状当作原因，或把手段当作目标。如果有更值得解决的问题，直接指出并说明依据和建议调整的范围。

## 4. 推演二阶和三阶影响
<!-- 检索：二阶｜三阶｜连锁影响｜跨模块影响｜架构取舍｜长期维护成本 -->

> 从直接效果继续推演二阶和三阶影响。优先看相关模块、用户行为、系统复杂度和长期维护成本会怎样变化，并指出哪些传导有证据，哪些取决于假设。

## 5. 跨领域寻找可借鉴方案
<!-- 检索：跨领域｜跨学科类比｜其他领域｜借鉴其他行业 -->

> 在其他领域找结构相似的难题和成熟解法，比较它们依赖的条件。把可迁移的做法用于当前问题，按目标、成本和约束判断哪个方案最合适。

## 6. 用最强反方检验方案
<!-- 检索：最强反方｜最强反对者｜反例｜证伪｜挑战现有方案｜压力检验方案 -->

> 先假设当前最看好的方案成立不了。站在最强反对者的角度，寻找可推翻它的证据、反例和边界情况。重新比较可用方案，并说明什么发现会改变选择。

## 7. 追溯 Git 历史和架构演变
<!-- 检索：Git 历史｜Git历史｜关键 PR｜关键PR｜架构演变｜历史包袱｜历史遗留 -->

> 做全库审查时，沿主要模块梳理整个仓库的 Git 历史、关键 PR 和架构变迁。找出重要设计最初解决了什么问题，辨别仍有必要的取舍、历史遗留和已失去原始用途的设计。对可能移除的代码，指出依赖、调用入口和验证办法。

## 8. 按接手成本评估代码
<!-- 检索：接手项目｜工程师接手｜新人接手｜代码交接｜认知成本｜命名混乱｜职责不清 -->

> 假设明天由一名能力很强、完全不了解项目的工程师接手。沿主要入口、新人常见任务和关键模块梳理上手路径，评估他需要补多少背景，定位命名混乱、抽象过度、职责重叠及依赖隐含上下文的地方。给出按收益排序的简化建议。

## 9. 分析近期最慢的 PR
<!-- 检索：最慢的 PR｜最慢的PR｜PR 耗时｜PR耗时｜PR 周期｜PR周期｜PR 性能回退｜PR性能回退 -->

> 分析最近 [N 天] 的所有 PR。先明确耗时口径，再找出最慢的几项并定位卡点。如果关注交付周期，核对等待评审、修改和构建各耗时多久。如果关注运行卡顿，用性能记录或可复现对比定位相关改动，并给出可验证的优化。

## 10. 复盘重复 Bug、返工和回滚
<!-- 检索：返工复盘｜回滚复盘｜重复 Bug｜重复Bug｜重复修改｜问题复盘｜故障复盘 -->

> 复盘最近 [时间范围] 的 Bug、返工、回滚和重复修改。对照具体案例找可预防的共同根因，给出相应的项目规则、自动化或 Skill，并说明各措施针对哪种重复成本、怎样判断是否有效。

## 11. 新项目先找成熟的开源参考
<!-- 检索：新项目｜从零开发｜开源底座｜开源参考｜开源方案｜GitHub 高星｜GitHub高星 -->

> 开始新项目时，先在 GitHub 等开源平台找相近的高星项目。比较功能匹配、许可、维护状态和接入成本，找出适合直接复用的模块或底座，减少从头实现的工作量。小范围修改沿用现有项目。

## 12. 控制代码复杂度
<!-- 检索：过度防御｜重复校验｜边界校验｜提前抽象｜过度抽象｜控制复杂度｜简化代码｜重构代码 -->

> 对发生概率很低、超出当前支持范围的边界或并发情况，说明触发条件、概率依据和影响，确认后再为它扩展实现。现有支持范围内的边界正常处理。
>
> 外部数据在进入系统时完成校验，内部用明确的类型和已建立的约束传递。单次使用的逻辑就近实现。需要处理具体异常时再用 try/catch，一个函数能清楚表达的逻辑保持完整。
